As we transition from acting as solo developers to orchestrating swarms of AI coding agents, our relationship with the code we are responsible for is fundamentally shifting. We spend less time writing code and more time reviewing specs and logic. In this new dynamic, a subtle problem is creeping into our repositories: the death of human readability by a thousand edge cases.

![The death of code readability](/assets/images/2026/Aug18-banner.jpg)

It's honestly a subtle problem with a not subtle effect. If you've spent any time reviewing code generated by a coding agent, you've likely noticed its inherent paranoia. LLMs are trained to be universally helpful and deeply defensive. When tasked with writing a function, they don't just handle the happy path; they exhaustively handle every conceivable corner case, null check, and type mismatch. Most of the time, those checks are just paranoia passed off as "defensive coding" or "defense in depth", but the cases the code handles are actually impossible because of the software architecture, type system, or routing logic.

In extreme cases, a piece of code that can be written in a few lines ends up with hundreds of lines of defensive `if/else` and `try/catch` blocks, or weird and wonderful ternary operators that will never and can never be exercised by tests. 

You may remember I recently wrote about [agentic testing](/posts/2026/2026-06-07-agentic-testing.html). The LLM wants to get to that green coverage indicator, so it writes exhaustive tests for all those impossible corner cases. There is no distinction between a test for the happy path, the test for a common failure, and a test for something that will never happen in the real world. So you lull yourself into a false sense of security, not understanding that you've created a fragile set of tests that don't actually produce meaningful results.

## The readability paradox

I'm writing a lot of [Hono](https://hono.dev) code these days. Take a standard Hono route written in TypeScript. If your middleware already validates incoming JSON, you know the payload is safe. You've also likely got an exception handler that converts any reasonable exception into an HTTP response.

An LLM agent, lacking the broader architectural knowledge, will often re-validate the payload, add `try/catch` blocks around operations that cannot throw, and return generic fallback states instead of letting the application fail fast. The resulting code is a mess.

To the AI, this loss of readability doesn't matter.

An AI will happily go hunting through transpiled and obfuscated code deep inside `node_modules` to find a weird corner case. Your 500-line file bloated with redundant null checks isn't going to deter it. The LLM doesn't get fatigued by visual noise, and it doesn't lose its train of thought when scrolling through nested conditionals. It can parse the core logic just as easily.

If we are moving towards a future where AI does the majority of the reading and writing, should we even care if the code is readable to us?

## Why human eyes still matter

While agents are incredibly capable, they are not yet fully autonomous maintainers. Most organizations require a human owner for code. When a complex runtime bug occurs, you are the one who has to debug it. Try to trace a logical flaw through defensive code is exhausting and slows down the debugging cycle.

There are more insidious problems though. Context windows are not free. With the current rash of changes in billing models by the major coding models, organizations are cracking down on indiscriminate token spend. Every redundant runtime check, unnecessary type guard, and padded fallback state consumes tokens. When you hand a file back to an agent to iterate on, that defensive coding style eats into the context limit, leaving less room for the agent to reason about the actual architecture.

## You are reviewing your agent output, right?

Beyond cheaper coding sessions and shorter debugging cycles, readable code acts as a force multiplier for team velocity, security, and long-term maintainability. Clean code allows new team members, including coding agents, to construct accurate mental models immediately without relying on tribal knowledge or out-of-date internal docs. When code clearly expresses its intent, engineers can refactor, extend, or replace modules with confidence, drastically reducing the risk of hidden regressions or side effects.

The simpler code is easier to understand. While this is good for developers of all skill levels, it is especially true for junior developers. If the LLM takes over the coding job and doesn't write readable code that junior developers can learn from, who is going to become the critical senior engineers in the future?

Simple code exposes security and architectural flaws quicker. The real dangers such as subtle bugs, edge-case race conditions, and security vulnerabilities hide easily inside convoluted hyper-defensive code. Clean code makes anti-patterns more apparent.

## Reclaim your codebase with `AGENTS.md`

We have to actively train our coding agents to stop being so paranoid. We need to define guard rails for when defensive programming is necessary and when it is just noise. 

In [my last article](/posts/2026/2026-08-14-agentic-setup.html), I built a typical `AGENTS.md`. Defensive programming requirements are an ideal capability to think about for your `AGENTS.md`. Here is how I start the work with most of my projects:

```markdown
## Coding Style & Readability

**1. Trust the Type System (TypeScript)**

- **DO** Assume strict mode is enabled and trust the compiler type system.
- **DON'T** write runtime type checks or defensive null checks for internal data passing if the TypeScript compiler already guarantees the type and safety.

**2. Trust the Infrastructure**

- **DON'T** revalidate data that has already been validated at the system boundary (e.g., inside middleware or API gateways).
- **DO** Assume data is clean if it reaches the core business logic.

**3. Fail Fast, Don't Pad**

- **DON'T** attempt to gracefully handle logically impossible states just to prevent an error.
- **DO** Throw a clear, descriptive error immediately. Errors are caught through universal error handlers.

**4. Flatten the Happy Path**

- **DO** keep the primary execution flow at the highest indentation level possible.
- **DO** handle errors and edge cases early and return/throw immediately with guard clauses.
- **DON'T** nest the "happy path" inside large `if/else` or `try/catch` structures.

**5. Omit "Just in case" code**

- **DO** write the minimum amount of code required to satisfy the immediate feature.
- **DON'T** add speculative database columns, extra function parameters, or placeholder variables "just in case" they are needed later.
```

Interestingly, when I got my coding agent to review this document, it got **VERY** defensive about these guard rails and wanted me to soften most of them. 

These may not be the right guard rails for your situation. In fact, they probably **WON'T** work for your situation. But they are a starting point. You should think about what you want your code to look like and provide similar guard rails for your situation. Nothing is set in stone. If you find your coding agent uses a specific undesirable code block, write a guard rail about that. Iteration is good.

## Final thoughts

By explicitly giving your agents permission to trust the environment they are building in, you strip away the defensive bloat. The code becomes lean. Your context windows stay uncluttered.

Your repository remains a place where human developers can actually read, reason, and build.

Unreadable code is technical debt.  Every redundant line requires continueous processing and testing overhead.  Readability directly reduces the total cost of ownership.  Treat readable, clean code as a prerequisite for effective agentic workflows.  Clean architecture yields dramartically higher accuracy from coding agents and automated test generators.

As a final note to my vibe-coding readers.  Readability is not something that will slow you down.  Rather, it 
is something that will keep your development speed as fast in month 12 as it was on day 1.  Readability allows you to ship faster.
